# 12 横切：实施批次、风险与完整执行示例

## 1. 实施批次与完成标准

工程量为相对判断，不是承诺工期。先修正确性，再测收益。下表把三份原文的批次合并，按依赖排序。

| 批次 | 内容 | 对应文件 | 完成标准 |
|---|---|---|---|
| M0 固定基准 | 明确当前版本、补 F01/F02 失败用例、清点协议与实际数据 | 00 | 能稳定表达 F01/F02，未知项有记录 |
| M1 P0 数字闭环 | MetricSpec、记录级重算、产物导入边界、Evaluation、资格有效性、文档数字核对、评测类型标签 | 04、05 | 错数字和过期证据不能产生 GO |
| M2 P1 判断语义 | inconclusive、disposition、候选/确认分级、保护指标、Type-A/B 门、停滞计数、obligation 账本、结果→claim 路由 | 06 | seed 上限不强制结论；旧状态正确迁移；OPEN 项阻断 GO |
| M3 P1 执行约束（平台无关部分） | D7 记账（Reservation、submission_key、幂等结算）、站点技能义务写进模板与 README、成本预估与超时 attention、配置去重、可选 webhook、Claude 端回执状态 | 01、05 | 并发准入和未知提交故障测试通过 |
| M4 P1 评审后端与候选复核 | `review_call.py`（pi 与 Claude Code CLI 两个基座）、`review` 文档类型与 `reviewer` 角色、两端 `research_review` 工具、`candidate_recheck`、复核清单、版本化复核 | 09、07 | 每个 GO 都能回答"基于哪次评估、检查了什么、谁复核" |
| M5 P1 想法 → 实验设计 | 问题锚点、假说文档必需章节、claim map 与实验块、`experiment_design` 文档、里程碑、`code_review` 与 sanity 规则、消融规划 | 03 | 节点创建前有完整设计；提交作业前有代码审查与 sanity |
| M6 P1/P2 发现流程 | 文献工具与存在性核验、`discovery_state`、`discovery_gate`、`candidates`、lens 子代理、planning 提示词分支、`create_hypothesis` 回执检查 | 02、08 | 用户只给方向也能立项；用户假说与新候选一起查新 |
| M7 P1/P2 经验复用 | finding / lesson 文档、`context_pack`、`capture_filter`、`threat_scan` | 08 | 重复故障下降，经验不越权、不无条件套用 |
| M8 P2 搜索与对照 | 关系边合并、探索预算、完整研究 benchmark | 06、11 | 固定资源下测到实际收益或明确无收益 |

M4 先于 M5、M6：代码审查、消融规划与查新都依赖评审后端。每个批次的完成标准另加 14 的实施协议：Fable 5.1 阶段末评审、Herdr 双宿主真实测试与终审全部通过。

### 1.1 首个可合并改动

首个 PR 不应同时重写整个状态机。建议内容为：新增基础指标重算函数、让旧 `record_verdict()` 交叉核验、补数字不一致测试，以及在 GO 查询/提交时检查当前依据。

即使完整 Evaluation 模型尚未上线，也应先让旧框架证据在框架变更后不再被误用于新 GO。临时修复不能只清空几个 UI 标签，而要覆盖项目决定的写入路径。

### 1.2 第二个可合并改动

正式引入版本化 Evaluation 与协议绑定，处理历史兼容；随后替换“达到 seed 上限必须定论”的规则。让旧文档、UI、提示词与两端适配器同步。

### 1.3 不阻塞修复的后置工作

大范围代码拆分、通用向量检索、复杂自动规划、更多宿主入口和自动论文生成都不能成为 P0 完成的前置条件。

## 2. 风险、取舍与暂不实施项

### 2.1 主要取舍

| 风险 | 缓解方式 |
|---|---|
| 独立确认提高成本 | 限定最终候选数量，预留小额确认预算；screening 输出不冒充确认完成 |
| 状态维度增加复杂度 | 只保留生命周期、证据、投入三种真实含义；旧显示标签作为派生视图 |
| 过于保守而错失候选 | 允许不确定与有限探索，不要求全部分支先达到推断级证据 |
| 过于宽松而持续追噪声 | 冻结确认候选、记录确认使用史、限制周期内确认数量 |
| 经验污染后续研究 | 适用范围、来源、反例和失效状态与经验一起检索 |
| 总预算预留降低资源利用率 | 按实际分配结算释放；优化预计值可以改善调度，但不替代准入上限 |
| 重算材料占空间 | 保留最小证据，而不是默认所有 checkpoint；最终候选专项保留 |
| 复核增加模板负担 | 风险驱动、短任务；自动计算项不再交模型重复签字 |

补充取舍：

| 风险 | 缓解方式 |
|---|---|
| 跨模型评审增加费用与延迟 | kind 分级 thinking；Claude 后端可用 `--max-budget-usd` 单次封顶；`review_usd_alert`；代码审查与消融规划可按配置关闭 |
| reviewer 与执行者同族时"独立"名不副实 | `require_cross_family` 默认开；身份来自 `turn_end.model`，不来自配置 |
| 设计阶段文档负担过重 | 必需章节只检查存在与关键字段；claim 与实验块数量有上限；分析类节点不强制代码改动 |
| 发现流程生成大量低价值候选 | 机械去重 + 预算门；triage 只决定进入查新的数量；候选不建节点就只留在报告中 |

### 2.2 明确不在本轮范围

不开发自动投稿，不建立常驻多角色评审委员会，不重新选图数据库，不做通用分布式工作流平台，不增加新的密码学审计体系，不把全部历史塞进向量库，也不预先引入 MCTS/强化学习调度器。

现有的文件版本校验可以继续使用，但不新增“必须完整防篡改后才能实验”的门槛。证据可重算与历史可追踪不等于需要全面事件溯源。

补充：不移植 ARIS 的论文/专利/海报技能、多 reviewer 后端路由、research-wiki 整体、aris-monitor、Vast/Modal/screen 启动、meta-optimize、安装脚本（13 §3）。

### 2.3 不能由插件统一硬编码的项目参数

最小实际收益、保护指标容忍度、确认样本数、统计推断假设、代理任务是否代表最终场景，以及不同硬件的资源折算方式，都必须来自具体研究计划。

这些参数应在立项时提出并由用户确认。不能在看到结果之后由 agent 自动降低阈值；也不应为通用插件写死一个对所有研究都适用的默认科学标准。

### 2.4 关于理论正确性与可发表性

可核查数字、规范实验与独立复核都不能保证顶会录用。Stage 1 GO 只表示当前证据支持继续投入；新颖性、重要性、外部有效性和完整实验仍需要后续研究。

本设计的目标是减少容易避免的错误与浪费，不宣称解决了自动科研中的所有判断问题。

## 3. 完整执行示例

下面是虚构示例，用于说明流程和状态，不是实际研究结果。

### 3.1 立项前（本包补充）

用户给出优化器改动作为种子假说并授权 100 node-hours。文献助手检索并核验 12 篇相关工作；lens 子代理围绕种子生成 9 个候选（变体、组合、竞争解释各若干）；跨模型 triage 选出 3 个；种子与这 3 个候选各做一次查新与批判性评审，其中一个候选被点名论文覆盖而淘汰并记入报告。Leader 为种子和 2 个新候选写假说文档（问题锚点、claim map、实验块、成本），请用户确认立项。

### 3.2 立项

用户提出一种优化器改动，授权 100 node-hours。Leader 定义短程后训练协议，准确率采用百分点差值，最小实际收益为 0.2 个百分点，训练时间允许最多 10% 退化。预留搜索 70、确认 20、修复 10 node-hours。

根节点 worker 实现并运行 baseline，冻结评测与统计工具。共享内核导入 baseline 的 run 材料，建立当前协议与 MetricSpec。

### 3.3 首轮探索

H-A 在一个 seed 上比 baseline 低 0.03 个百分点。系统保留真实差值，结果为 inconclusive，而不是自动宣布理论失败。Leader 认为额外重复可能改变选择，允许少量补充。

H-B 出现较大正向收益，但诊断显示实际训练 token 数更多。共享内核拒绝与原协议直接比较，将其标为协议不匹配；修正后重新实验，不把错误结果写成发现。

H-C 没有单独收益，却表明 H-A 的某个稳定性前提不成立。Leader 提出 H-D，记录 repairs(H-A) 与 tests_assumption(H-C)，在预算内验证一个具体修复，不伪造父节点正向结果来获得扩展许可。

### 3.4 故障与恢复

H-D 的训练提交超时。Reservation 保留，提交状态为 unknown。脚本通过 submission_key 找到原 job_id，继续监控；没有再提交第二个作业。

worker 会话退出后按原身份恢复，科研 attempt 不变。作业结束，脚本导入实际用量，预算结算一次。

### 3.5 候选确认

H-D 的探索重复显示值得投入，进入 candidate_ready。冻结代码与配置后，在未用于选择的确认 seeds 上运行，同时检查需要的确认数据切分。

共享内核从原始输入计算确认差值并检查保护指标。另一个短复核任务检查方法—代码一致性、最近邻工作和论证范围。

若确认均值未达到门槛或仍不确定，保留候选及局限，不把门槛调低。若满足预定 Stage 1 gate 且必要复核有效，Leader 作出 GO，并列出 Stage 2 要验证的外部适用性问题。

### 3.6 后续证据变化

若后来发现评测器实现有误，更换协议后旧 Evaluation 不再支持当前 GO。历史报告仍保留，追加失效说明。

项目不会自动进入 Stage 2，也不会因为失效而重开训练；用户决定是否投入新的范围和预算。

## 4. 结论

research-tree 当前已经具备可用的研究管理骨架。下一步应优先增强"实验事实怎样约束结论"，而不是扩张"自动研究"表面的功能范围。

**第一优先级：从输入重算统计值；把 GO 资格绑定到当前有效证据。**

**第二优先级：允许不确定；分离科学证据与投入处置；为少数候选保留独立确认预算；用跨模型评审替代自评。**

**第三优先级：把想法到实验设计的过程结构化；让发现流程与经验复用改善后续选择；再通过完整研究对照证明收益。**

本设计包完成的是设计和来源整理，不包含代码修改、测试运行或任何新的实验授权。
