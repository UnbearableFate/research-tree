What holds up:

- **F01/F02 expressed on the baseline.** The three `KnownDefectTest` cases fail for the stated reason by code reading, not by an incidental error:
  - `record_verdict` (`research_db.py:1038-1082`) never reads `run.metric_value`.

- **No host drift.** Nothing under `claude-mod/` or `codex-plugin/` is in the changed list, and the only `shared/` change is the test file.
- **Test counts.** The files hold 76 shared test methods (73 + 3 new), 4 packaging and 13 Codex adapter tests, matching the log.
- **Inventory table.** The rows I checked in §3 of the log (metric direction, seed-only pairing, parent reference resolved at verdict time, `alert_node_h`) match the code.
- **Scripts.** `stage_review.py` matches the 14 §3 command and validity criteria, and the generated `plan.md` and `research-tree.yaml` fit the current init check and config schema.

What needs fixing:

1. **M02 test is confounded.** It reuses `evaluate()`, which sends mean 70.3 against runs of 70.0 and asserts a bare `ResearchDBError`. Once M1 adds the summary check it passes without any delta recomputation.
2. **The data inventory states a false fact.** The log says the demo's `metrics.json` files survive cleanup. No such file exists under `demo/`, and `make_demo.py` never writes one.
3. **`stage_review.py` can record an unparsed review as clean.** When the findings JSON cannot be parsed, the record still says valid with 0/0/0 findings. That record is what 14 §6 uses for batch completion.
