**Review of the Codex real-host infrastructure batch (M0, M6)**

I read the design files (01, 02, 09, 10, 11, 14), all sixteen changed files, the Codex adapter tests, the shared discovery/review/test modules they depend on, the packaging tests, the Claude adapter for parity, and the batch's own test logs and review records.

**What holds up.** The Codex hook now records an observed model on SessionStart and PostToolUse per actor and session, deduplicated, and the wrapper's `leader_model` reads exactly those records, so a project initialised inside a live Codex session can satisfy 09 §2.1 step 3. The adapter test for that drives the hook through a real `research_tree.init` and asserts via `review_call.leader_model`. The three Codex timeouts are correctly ordered (3600 wrapper, 3800 server subprocess, 3900 client in both `.mcp.json` and the exec config) and pinned by a test. The six-tool set in the install check equals `codex_mcp.TOOLS`. The message-type enum in the `research_message` schema equals the shared message schema's enum, and the runtime gives an actionable error for `blocker`/`notice`. The new `research_control lens` entry is gated on planning phase, `discovery.mode: full`, a configured lens and `models.lens_assistant`, gets a fixed `assistant/lens_*` identity, read-only sandbox, read-only database access, no messaging, no review, and the exclusive per-identity lock; two tests cover those boundaries end to end through the production `Runtime` and the real supervisor subprocess. The read-only allowlists of both hosts are still tied to `research_db.READ_METHODS` by the packaging test. The M4 review record now carries the erratum the previous round asked for.

**Gaps.** The main one is host drift created by the lens work: the shared rules now say the lens assistant is a read-only subagent on both hosts, but the Claude lens agent is registered with the `Write` tool and its spawn is not gated on phase, discovery mode or configured lens, while Codex enforces all of that. The two hosts also prescribe different shard semantics (`generator: "assistant"` on Claude versus the actual helper model on Codex; the Codex lens output format omits `closest_work` and `dedup_key`). Second, the batch's own records state that the 14 §4 scenarios for M0 (root worker sanity, baseline, freeze) and M6 (D2–D8, two-column report, user-seed ABANDON) have not passed on Codex, so under 14 §6 the batch is not complete; the records say so honestly, but a final review must not close it. The rest is documentation: the Codex skill still says workers always run workspace-write, the root README still marks `models.lens_assistant` as Claude-only, the plan template tells users `precheck` is acceptable for a direction-only plan (precheck skips candidate generation, so nothing would be found) and still points at a version-1 `stage1` key, and the `research_message` tool schema has no required list.

2. MAJOR：M0/M6 当前未完成属实；保持进行中。根流程、发现报告和用户种子场景有实际结果后才申请终审。

4. MINOR：技能补充 worker 原生 Full access 继承条件，UI/lens 始终只读。
5. MINOR：README 移除 lens_assistant 仅 Claude 的说明。
6. MINOR：方向-only 模板要求 full；version 2 收益门提示改 metric_specs.minimum_practical_gain。
