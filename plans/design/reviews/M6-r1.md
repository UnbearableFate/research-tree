**Review of batch M6**

The shared core for M6 is substantial and mostly matches the design: `discovery.py` ports the ARIS stage state and gate with the "done vs accepted" split, `literature.py` implements search, three-layer verification, PDF cache and front matter, `research_db.create_hypothesis` checks verified literature and candidate receipts, and both hosts block `confirm_request` until the gate passes. Test ids R09 to R13 and R15 to R17 exist and exercise the named behaviours at the module level. The literature tests are offline and cover the fallback order, lookalike titles and the unverified path well.

The main problems are in the joints between the pieces. The gate requires each selected candidate to carry a `literature` list of document ids, but nothing in the merge, feasibility or select steps, the lens shard schema, or either planning prompt ever writes that field, so in `full` mode the gate blocks every lens candidate unless the Leader hand-edits `candidates.json`. In `precheck` mode the opposite happens: `selected` is only set by `select`, which needs a triage review that precheck skips, so the gate's per-candidate checks run over an empty list and pass vacuously. The gate test writes `selected` and `literature` into the candidate file by hand, which is why neither gap shows up. The design's error codes `PRECHECK_REQUIRED` and `LITERATURE_UNVERIFIED` are not used; a missing receipt is reported as `REVIEW_UNAVAILABLE`, which means something else. The two hosts drift on candidate generation: Claude registers a read-only lens subagent driven by `models.lens_assistant`, Codex has the Leader write the shards itself and ignores that model setting. Literature verification is enforced from a front-matter line that any literature author can type, with no `verify_literature` interface binding the verification to the registered document. The confirmation gate on both hosts and the discovery CLI have no unit tests. Several config keys and docs are out of sync at the minor level.
